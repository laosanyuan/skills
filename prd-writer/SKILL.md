# PRD Writer

把用户的产品意图写成可讨论、可实施、可验收的 Markdown PRD。以用户已确定的范围为准，不把建议、猜测或实现方案写成产品事实。

## 工作方式

1. **定位并阅读上下文**：优先使用用户指定的文件、选中内容或明确的当前文档，不要求文件名必须匹配 `PRD-*.md`。未指定时用 `rg --files` 查找相关 PRD；仅在无法从上下文唯一确定目标时询问。已有内容先读相关功能、公共规则和依赖，再修改。
2. **区分已知与未知**：从需求原文、已确认对话和已有 PRD 提取事实，不让用户重复回答。判断缺失信息是否会改变核心行为、验收口径或范围。
3. **只澄清真正阻塞的决策**：每轮聚焦 1–3 个重要问题，合适时给出选项及影响。信息已充分时直接写；用户明确授权“你来定”时在授权范围内做取舍并注明依据，不再逐项索要同一授权。用户未回应、离线或测试场景均不构成默认决策授权。
4. **按授权深度产出**：核心流程尚不明确时先询问，不把完整 PRD 伪装成已定稿；用户要求先出草稿时，可写确定部分并集中列出待定项。不阻塞整体的细节保留待定，避免无休止追问。
5. **一致性检查并交付**：核对编号、依赖、规则、验收标准及图文；告知文件完整路径、改动功能和仍需决定的事项。不要声称待定项已经确认。

本技能只负责 PRD 内容。若请求不属于此范围，不强行生成 PRD，也不要求用户再次确认原本清楚的任务；直接按适用工作方式处理。混合请求先完成需求部分，再继续用户已要求的后续工作，不能因阶段切换重复索要许可。

## 需求澄清与事实边界

按功能涉及的实际问题检查，而非把每一项变成必答问卷：

- **用途与范围**：谁在什么情况下完成什么目标，入口、输入、可见结果；包含什么，容易误解但明确不包含什么
- **流程与权限**：主路径、必要分支、角色权限、取消/返回、重复操作、失败后的可恢复状态
- **交互状态**：与当前功能相关的加载、空、成功、失败状态；没有 UI 的能力不强加页面和提示文案
- **计算口径**：统计/排名的样本与去重、时间与时区、跨日归属、金额精度与舍入、状态切换条件。只有涉及这些概念才深入追问
- **操作结果**：对可能改变业务状态的操作分别检查成功、明确失败与结果未知，不能只覆盖创建而遗漏取消、撤销等相关操作。超时或连接中断不等于业务失败；说明如何核实真实状态，以及核实前后是否允许重试，不凭空承诺完成时限。异步操作还应明确受理与完成的判据及迟到结果处理；纯本地且结果确定的操作不强加异步流程
- **重要约束**：涉及敏感数据、资金、不可逆操作、容量或可用性时，识别必要的需求缺口；未知值写待定，不为显得专业编造指标或合规结论

具体文案可给示例，不必逐字追问。图标、配色、动效等不属于当前决策时不展开。手机号位数、验证码期限、地区、币种、性能时限等会约束产品行为，不能当普适默认值。

对影响实现或验收的未确认内容，在对应位置使用以下标记，并在结尾集中汇总：

```markdown
> 待定 Q01：删除记录后是否支持恢复？影响 F002 的删除流程与验收
> 建议方案 Q02：允许用户手动重试失败请求（待用户确认）
```

建议未确认时不写成“必须”。若用户授权采用建议，可记为“决策依据：用户授权选型，采用……”，无需保留虚假的待确认状态。需求来源用简短说明或链接关联到有争议/重要的约束，不为每句常识增加追溯字段。

## 新建文档

尊重用户指定的路径与命名；未指定时使用当前工作目录下的 `PRD-[产品名].md`。缺少正式产品名但不影响需求时可使用描述性暂名并说明。已有同名文件先读，不能覆盖不相关文档。

内容按复杂度裁剪。小功能不需要空章节；用户只提出一个能力时不要机械扩展成多个功能、完整平台或额外 backlog。用户明确要求的范围应完整覆盖，不用“先做核心”擅自删减。

跨功能公共规则集中定义，功能详情引用并补充差异；总览流程、字段表只在提供额外信息时添加。验收用例仍保留必要条件与预期结果，不为缩短篇幅删掉关键边界。

````markdown
# [产品名] PRD

> 最后更新：YYYY-MM-DD
<!-- prd-id-high-watermark: F001 -->

## 概述

- 目标与用户：[解决谁的什么问题]
- 本次范围：[明确包含的能力与必要边界]

## 功能列表

| 编号 | 功能名称 | 需求状态 |
|------|----------|----------|
| F001 | [功能名称] | 已定义 / 草稿 |

## 功能详情

### F001 - [功能名称]

**功能描述**：[目的与用户可见结果，不展开技术实现]

**前置依赖**: 无

**使用场景**：[角色、触发条件与目标]

**交互流程**

1. [操作或事件]
2. [系统可观察的反馈与结果]

**异常与边界**

- [相关失败条件、反馈及是否可恢复]
- [已确认的限制；容易混淆时说明不包含什么]

**验收标准**

- AC-F001-01：给定[前置条件]，当[动作/事件]，则[可观察结果]
- AC-F001-02：[关键失败或边界场景的可观察结果]

## 待确认事项

| 编号 | 问题或建议 | 影响范围 |
|------|------------|----------|
| Q01 | [未决问题；没有则省略本节] | F001 |
````

### 可验收，而不是假精确

每个已定义功能至少有能覆盖主路径的验收标准；按风险补充关键失败、权限、边界和恢复场景。不机械增加数量。使用 Given/When/Then 或等价清晰表达，避免“体验良好”“快速”等无法判定的词。

可观察行为不一定要数字：如“提交处理中禁止重复提交，失败后恢复可操作状态”即可验证。确需性能指标时说明测量条件、口径及来源；没有依据时标待定，不能随意改写成“300ms”“2 秒”。不在产品需求中预设数据库、协议、框架或算法实现，除非它们确实是用户给定的约束。

验收 ID 在迭代中保持稳定，新标准追加编号，不因排序变化重编。被替换的要求与关联验收需同步更新，不能让正文与测试预期相互矛盾。

涉及状态变化的验收，按“初始状态 → 事件顺序 → 每步可观察结果”走读正文和用例。例如上下文改变已触发选择迁移后，下一次操作应基于迁移后的状态；不要在验收中又隐含沿用旧状态。不为每个简单功能增加状态表。

## 编号、依赖与优先级

- 新建功能 ID 默认从 `F001` 递增，超过 `F999` 后用 `F1000`；已有文档的编号体系优先沿用，排序或修改不能重编。正文和下游设计引用同一 ID，不为适配脚本改号。
- 文首 `<!-- prd-id-high-watermark: F023 -->` 记录**曾分配的最高号**；新增从此值与现有最大值中的较大者加一，删除不降低该值。不复用已删除 ID，也不留下可误读为待开发功能的“已废弃详情”。
- 旧文档首次采用编号元数据时，先从当前内容及可靠的既有编号记录确定最大值；若过去删除的编号无从得知，说明历史基线限制，不声称已验证从未复用。保留用户已有等效编号登记方式。
- 依赖是“该功能交付所必需的前置能力”，不是“相关功能”。按 ID 明确列出；循环依赖需要澄清、合并边界或拆出共同前置能力，不能靠排序掩盖。
- 用户要求 MVP、排序或分阶段时使用优先级；已有优先级保留其定义。无既定约定时：P0 为核心必需，P1 为重要，P2 为可选，P3 为远期。产品优先级不是开发阶段编号。
- 前置能力必须不晚于依赖方可用。通常 P0 功能不应依赖尚未安排的 P2 功能；不能把 P 的数值大小理解反。若已有替代能力、裁剪方案或独立交付计划，应明确说明，不自动重排用户优先级。

需要脚本检查时，使用以下**单行字段**；解释写在下一段，避免把说明混入 ID 列表：

```markdown
### F003 - 导出记录

**前置依赖**: F001, F002
**优先级**: P1
```

## 增量变更与冲突处理

用户明确要求替换旧规则时，该替换本身已获授权，不用引用旧规则再确认一次。先检查关联功能、公共规则、依赖、验收与图，再同步必要改动。若变更同时涉及未授权的取舍（例如删除登录后，哪些页面改为公开），引用具体条款，说明影响并只询问该缺口。

动笔前从原文区分本次要替换的规则与仍须保留的约束，尤其留意“仅、不得、最多”等限定；改后按来源条款核对实际正文，不能只在变更记录中声称保留。新增查询、下载或恢复能力不默认授权扩大数据收集、可见范围或留存字段/期限；区分当前处理所需的临时明细与长期记录。若新能力与既有限制确实冲突，明确指出冲突及待决部分，不自行放宽旧约束或编造新的留存期限。

- **新增**：复用已存在的能力，避免同一需求分配多个 ID；分配新 ID 时同步最高号、功能列表及详情
- **修改**：只改相关内容，保留用户结构和无关编辑；调整指标或业务规则时同步验收与待定项
- **删除**：先查谁依赖/引用目标，以及其验收和图示。能依据用户意图确定的影响一并处理；无法决定下游行为时先询问，不能先删除、留下断链再问。删除后保留最高号元数据，移除相关列表与详情
- **撤销**：只逆向本次授权修改并保留其他编辑；不以整文件或 Git 回滚代替内容级撤销

更新实际日期。需求状态描述“草稿/已定义”等定义成熟度，不擅自标记实现已完成。已经明确的跨文档影响可汇报或按授权更新，不能悄悄改动无关交付物。

## Mermaid：只画能减少歧义的关系

线性短流程用文字即可；复杂分支用 `flowchart`，跨角色消息用 `sequenceDiagram`，状态与合法迁移用 `stateDiagram-v2`。图放在相关功能下，补充文字里的条件、异常和验收，不替代它们。

- 节点标签短而清楚，详细规则放正文；分支边标明条件，不把多段说明塞进一个节点
- 图文使用同一套角色、状态与条件；状态迁移明确触发条件，必要时描述取消、失败、重试与迟到事件
- 状态图按真实生命周期画起点与终点；长期运行、循环或局部状态模型不必虚构终态
- 时序图的 `-->>` 通常表示虚线返回消息，**不等于异步语义**；异步处理需在消息/注释和正文中明确回调、轮询或通知及完成判据
- 只对实际生成的图检查语法与关系；没有渲染工具时说明未渲染验证，不声称图已成功渲染

## 交付前检查与辅助脚本

交付前对实际文档核对范围、验收、待定项及图文一致性。文档使用可识别的 F 编号时，可运行以下只读脚本（Python 3.10+ 标准库，无需联网）。它直接读取指定文件，包含尚未被 Git 跟踪的新文档；`git diff --check` 不能代替新文件内容检查：

```text
python -B "<skill-root>/scripts/check-prd.py" "<PRD 文件绝对路径>" --json
python -B "<skill-root>/scripts/check-prd.py" "<已有 PRD 文件绝对路径>" --id-style existing --json
python -B "<skill-root>/scripts/check-prd.py" "<修改后 PRD 绝对路径>" --baseline "<修改前 PRD 副本绝对路径>" --json
```

`<skill-root>` 是当前加载的本技能目录。脚本识别顶层围栏外 `##` 到 `######` 的 `F数字 - 标题`、`F数字 标题` 或冒号分隔标题，以及上面的单行依赖/优先级字段和编号元数据；不把表格和正文引用当作功能定义。默认按 F001 起的格式检查；`--id-style existing` 允许已有 F1/F01 等正数编号，仍按原文匹配引用，不自动将 F1 与 F001 互换。

检查重复 ID、悬空依赖、自依赖/循环、最高号过小及顶层围栏未闭合；优先级倒挂和未覆盖字段作为警告。多行依赖、非 F 编号或其他布局人工核对，不为检查器重排旧文档。它不验证业务语义、任意正文引用、验收覆盖、链接、列表/引用块内部 Markdown 或 Mermaid，也不能证明历史 ID 未复用。退出码：`0` 已覆盖检查无错误（仍可有警告），`1` 发现错误，`2` 输入/读取失败。

增量更新需要编号与原文保留证据时，修改前在临时目录保留原文副本，或使用用户提供的可靠基线，再以 `--baseline` 比较；已有短编号可同时加 `--id-style existing`。脚本不生成基线、不修改文档，也不从修改后内容倒推原文。它列出功能标题和单行 `AC-F001-01：文本` 的新增、删除、修改，以及围栏外被替换/删除的正文行；这些是人工核对候选，不代表变更错误或业务约束已保留。最高号降低/移除、在基线已知编号上界内新增功能 ID 会报错；只能证明违反追加编号约定，不能断言更早历史是否复用。损坏基线会报错并停止比较；无可识别 AC 时明确提示未覆盖，不为检查器强加文档结构。即使返回 `0`，仍要按授权核对候选，并检查新增内容是否与未修改的原约束冲突，不能用文本差异替代业务判断。

按报告修复实际问题，警告逐项确认是否影响本次交付；文档未变时复用已有检查，不重复全文审查或另建等价检查脚本。达到请求范围与深度后交付文件路径、变化和未决项。如实区分“编号/围栏检查通过”“业务规则已人工核对”和“需求已确认”，不把未执行的检查算作通过。
