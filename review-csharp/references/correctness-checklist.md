# C# 行为、生命周期与设计审查要点

这里列的是追踪方向，不是看到相应语法就必须提出问题。先确认项目版本、调用契约及实际可达路径，再判断后果；不适用的领域跳过。

## 值、集合与控制流

- 检查 null/空集合、边界值、重复键、比较器、大小写与文化、排序稳定性和单位转换。Nullable 标注或 `!` 不提供运行时保护，但明确的上游校验也不能被忽略
- 区分整数除法、溢出、舍入与业务允许范围；浮点相等可能用于精确哨兵，金额类型也要按现有精度/舍入契约判断，不自动要求 epsilon 或更换数值类型
- 跟踪提前返回、异常和 finally 是否保留了必要状态转换。先写状态再执行可失败操作时，检查部分成功与重试是否使状态不一致
- `IEnumerable` 的延迟执行可能改变异常时机、重复 IO 和资源使用期；`IQueryable` 要核实实际 provider 的翻译与执行边界。不把 `ToList()` 当成通用修复，也不把每次多重枚举都判为 bug
- 集合或 record 的相等语义、可变字典键、返回可变共享集合会影响查找与调用方状态；先确认业务是否依赖值相等、快照或引用身份

## 异步、取消与并发

- 检查任务是否被等待、返回或纳入明确的后台生命周期，失败能否被观察；fire-and-forget 需结合宿主、异常处理及停止过程判断。`async void` 事件处理器是合法场景，不能一律报错
- 取消请求不等于操作已经停止。核对取消令牌是否传入实际等待/IO、取消是否与超时/普通失败区分，以及退出前是否仍有任务使用已释放资源。独立后台任务可能有自己的令牌，不强制传递请求令牌到所有操作
- `Task.WhenAll`、限流和部分失败要结合所有启动的任务及清理路径看；不能因其中一个任务报错就假定其他任务已取消或没有副作用
- 对 `.Result`、`.Wait()`、同步阻塞异步和同步上下文，用具体调用链说明死锁、UI 冻结或线程池压力；没有上下文证据不声称必然死锁。`ConfigureAwait(false)`、`Task.Run` 不是必须处处使用的规则
- 共享状态检查真实并行入口、锁的覆盖范围、原子性、内存可见性和锁顺序。`volatile` 不使复合操作原子化；线程安全集合不保证多步业务事务，也不保证 `GetOrAdd` 的工厂只执行一次
- `SemaphoreSlim` 的释放要对应成功获取，取消前未获取不能无条件 Release；同一 `ValueTask` 的重复消费是否合法取决于实际提供方，不按 Task 的保证推断
- UI/设备/图形对象的线程亲和性、事件回调重入及停止/启动交错按实际框架检查。不要把普通服务的上下文行为套到桌面 UI，也不要反过来

## 生命周期与资源所有权

- 沿创建、注入、借用、返回及缓存路径确定所有者。调用方/DI 容器拥有的资源不能仅因实现了 IDisposable 就要求局部释放；需要自己释放的对象检查成功、失败、取消路径
- `using` / `await using`、流、数据库上下文和枚举器的生存期应覆盖实际使用；重点查看返回流、返回未完成任务、延迟枚举及后台回调是否越过释放边界
- 停止或 Dispose 时核对停止信号、在途工作结束与依赖释放的顺序是否符合资源契约，覆盖退出异常和竞态；释放 socket 等资源以中断阻塞 IO、随后等待循环退出可以是合法顺序。幂等释放与并发释放需要契约证据，不为每个类要求终结器
- DI 生命周期匹配、singleton 捕获 scoped 服务、共享 `DbContext` 的并发使用按真实注册及作用域判断；不能仅凭类名推断注册方式

### 事件、订阅与重复初始化

- 从实际宿主追到注册入口和退出路径：首次创建、重复 Start/Attach/Loaded、部分初始化失败后的重试、切换发布源、Stop/Unload/Dispose。确认哪些顺序确实可达，注册是否幂等、失败是否撤销已完成的注册、清理是否由宿主真正调用；仅存在 Dispose 方法不是已经清理的证据
- 对候选核对“发布者实例、处理目标/方法、注册次数、移除次数”。普通 .NET 多播事件允许重复添加，单次 `-=` 只移除最后一个相等匹配；Start 两次后 Stop 一次可能仍有残留。读取事件自定义访问器或事件总线的实际语义，不将普通事件规则套到去重/弱引用实现
- 解绑需要同一发布者及相等的委托，不能只数 `+=`/`-=`；同一目标对象的同一实例方法重新转换成委托可正确解绑，并非必须引用同一个委托对象。另写一个形似相同的 lambda 不保证相等；核实闭包和保存的委托、IDisposable 订阅句柄或框架管理的释放路径
- 重复回调、退出后仍响应和对象保留可能来自同一个注册失配，应合成一条说明影响。解绑不等于在途回调已结束；回调访问已释放资源时，还需追踪停止、取消和等待协议，不把盲目先 `-=` 再 `+=` 或新增终结器当成通用修复

### 内存保留与后台工作

- 指出实际强引用链，如“进程级发布者/静态集合 → 委托或闭包 → 页面/会话及其缓冲区”，核对业务生命周期结束后哪条引用仍未移除。无边界集合需说明每次操作增加什么、何时应淘汰、现有上限/失效机制为何不能阻止增长；没有实测不编造泄漏速率、堆大小或必然 OOM
- Timer、后台循环、未完成任务、CancellationToken 注册和订阅句柄可能延长对象寿命。检查创建者、持有者和结束路径，取消是否会被观察、任务是否最终退出、回调是否仍捕获对象；任务完成后的正常释放不能误判为永久泄漏
- 区分托管对象意外保留、未释放的非托管资源和有界/约定保留的缓存。GC 能收集整体不可达的事件循环引用；局部事件未解绑、匿名 lambda、实现 IDisposable 与否或一次内存上涨，本身都不是泄漏证据。借用资源、同寿命订阅或经核实的自动/弱订阅不强制额外释放

## 外部副作用、恢复与数据一致性

- 文件替换、数据库更新、消息发送和远程调用跨多个步骤时，检查异常点、事务范围、部分提交、幂等键和恢复路径。数据库事务不自动覆盖外部请求或文件系统
- 重试是否可能重复扣费、发消息或覆盖状态；明确失败时操作有没有可能已成功。指数退避、补偿或 outbox 只在实际交付/一致性需求下建议，不当成所有系统的必选架构
- 数据库跟踪与并发令牌、事务隔离、唯一约束和批量查询要按实际持久层及支持的并发场景判断；应用层“先查再插”不能自动证明唯一性
- 检查排序、分页边界、时间类型与时区、序列化和文化格式是否使持久化/协议结果变化；“统一 UTC”不能替代本地日历或业务日期语义

## 安全与兼容性

- 从不可信输入追到 SQL、命令、路径、模板、反序列化和出站请求；检查参数化、规范化、授权和允许范围。只提与本项目攻击面相关的问题，不复制通用漏洞清单
- 检查对象级/租户级授权是否在实际敏感操作处生效，不把“已登录”当成资源访问许可；同时核对已有中间件和数据层约束，避免重复误报
- 文件路径、归档解压和符号链接的边界需要真实目标路径证据；日志、异常与调试输出不应暴露实际密钥或敏感个人信息。报告只给位置和必要的脱敏片段
- 公开签名、默认参数、序列化字段名、枚举持久化值、反射/XAML 绑定、源生成器输出及字段布局可能有外部消费者；比较实际契约，不以重命名“更规范”为由忽略破坏
- 对 AOT、裁剪、跨平台 API、目标框架及语言版本，只审查项目声明支持的环境。反射或平台专用 API 不是天然违规；需要具体发布配置与调用证据

## 设计合理性与可维护性

不是只检查立即可复现的 bug，也不是给任何长方法开重构清单。沿一个真实业务操作，从入口跟踪决策、状态写入、外部调用和退出；必要时简要列出状态转换或依赖关系，定位需要同时理解/修改的耦合点。

| 审查信号 | 值得报告的具体依据 | 不足以判错的情况 |
|---|---|---|
| 面条式控制流 | 分支、回调和跨方法可变标志共同控制流程，同一状态多处写入；确认一次操作的状态或失败收尾必须追踪多条相互依赖路径 | 方法较长、嵌套较深、存在 switch/goto；线性且内聚的解析/映射流程可能很清楚 |
| 重复业务规则 | 同一业务概念在预览、提交、重试等路径各维护一份，当前规则改动必须同步多个位置；或副本已出现语义分歧 | 相似代码分别承担不同契约；一律抽成带许多开关的“通用函数”可能更差 |
| 职责与副作用耦合 | 纯决策/计算与 UI、设备、持久化相互交织，使现有规则验证必须启动真实依赖，或独立业务变化会牵动无关流程 | 一个协调类顺序调用不同组件；没有接口或依赖注入本身不是缺陷 |
| 隐式顺序与共享状态 | 一次操作的中间数据散落在实例字段，无参数步骤隐式读写这些字段，多个入口各自维护初始化与调用顺序；修改或验证一步必须反查这些位置才能确定输入、输出和状态是否重置 | 有明确生命周期的领域状态，或单一内聚流程中的局部步骤；字段存在本身不是设计问题 |
| 过度抽象与依赖反转失当 | 为追踪一项现有规则需穿过无独立语义的转发层，布尔开关组合隐藏不合法状态，或双向依赖让局部修改难以隔离 | 层数或接口数量较多；能明确承担框架、边界或兼容职责的层不能仅按数量删掉 |

已知单线程、入口正确重置状态或上游顺序保证，可以排除相应的竞态、串单或未初始化故障，但不能单独反驳结构上的维护代价。分开验证“当前执行是否正确”和“现有规则/步骤的修改是否需要同步理解多个状态写入点”；后者仍需具体证据，不把所有有状态对象或私有辅助方法判成面条代码。

每项给代表性代码位置、现有修改/测试场景及最小改进边界，例如统一已确认相同的业务决策、隔离决策与执行、让一个组件拥有某个状态或订阅。建议保留调用顺序、异常/取消、外部副作用及公开契约；不要只说“拆小方法/加注释”，也不把状态机、设计模式、DI 或整体重写当必选答案。已证明行为错误的结构根因在功能项中说明，不再另算一条“设计问题”；只有结构证据时标明当前代价和风险，不虚构已经发生的故障。

### 大段复制与复用边界

- 对新增/修改的连续业务流程，按实际职责搜索相关入口中的副本，不限于逐字相同；改变量名、换常量或少量包装后的近似复制也需比较。只扩展到理解当前复制关系所需的范围，不借机审计所有无关历史代码
- 确认同一职责的大段手写逻辑被多处复制时，即使当前结果一致，也作为设计问题报告并建议抽象复用。给出至少两个代表位置、共同决策/处理步骤、实际差异，以及修复或规则变化必须同步多处的代价；不能只用“重复若干行/相似度高”判定，或建议继续把修复复制到每份
- 优先提取真正共同的规则或流程，让入口仅保留必要差异。可选择方法、结果类型、组件或适用的 XAML Style/Template；说明状态、事件/取消/异常、副作用顺序和外部契约如何保留，不用大量布尔开关、继承层或复制另一套通用代码掩盖差异
- 区分业务职责相同与外形相似。不同协议、平台约束、独立规则、生成/第三方代码和有必要独立表达预期的测试数据，不因相近片段就强制合并；若是否共享同一契约无法确认，先核对调用者和需求。多个副本归为同一根因，已因该根因报告行为失配时不再重复计一条复制问题

## 性能与测试

- 先找有规模依据的多余查询、热点分配、重复解析、阻塞与无界队列/缓存；区分 UI 响应、吞吐和延迟需求。短字符串拼接、LINQ 或 async 不是独立缺陷
- 给出规模或调用频率及增长路径；没有实际测量只能陈述相应复杂度或多余工作，不宣称实测提速。建议缓存时考虑失效、内存及并发语义
- 测试应能触发所报告路径并观察具体结果、异常、状态或副作用；看断言是否缺失、任务是否等待、mock 是否绕开真实路径、测试是否实际发现。并发测试避免把偶然 sleep 成功当可靠复现
- 建议最小反例，如特定空输入、失败注入或确定线程交错；不要求每个问题配整套新测试框架。看不到现有测试或无法运行时如实说明，不虚构覆盖缺口或已通过结果
