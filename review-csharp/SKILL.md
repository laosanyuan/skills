# C# 与 XAML 代码评审

找出值得作者处理的问题，说明触发条件、实际后果和修复方向。以代码、调用方和需求契约为依据，不把个人偏好、检查清单或“可能更好”当成缺陷。

综合 review 既检查行为正确性，也检查资源生命周期与设计合理性，不以“能编译、当前能运行”作为结束条件。设计问题不必等到故障发生才报告，但必须指出现有结构造成的具体维护、扩展或验证代价；格式检查放在这些审查之后。

## 1. 确定评审对象

| 请求 | 默认范围 |
|---|---|
| 评审提交、分支、PR 或 diff | 检查指定变更及理解其影响所必需的调用方、配置和测试；重点报告本次引入或激活的问题 |
| 评审文件、目录或代码片段 | 检查目标现有实现，不假定它代表某个提交或整个工程 |
| 只看 bug、安全、异步、性能等 | 限定对应主题，不附加全量格式审计 |
| 只看设计、可维护性或代码异味 | 检查职责、状态、依赖与控制流的实际代价，区分结构风险和已确认故障，不附加格式审计 |
| 只看格式、命名或注释 | 只按本包格式规则审查；不自动执行格式化 |
| 评审并修复 | 先识别问题，再执行明确授权的修复；新的契约取舍单独确认，不将此请求退回成只读报告 |

普通 review 到报告为止：不修改源码、测试、项目配置或技能，不自动提交、安装依赖或向 PR 发布评论。用户指定输出文件或明确要求修复时，仅执行相应授权部分；格式修复可使用可用的 `format-csharp`，结构重构可使用 `code-refactor`，缺少它们不妨碍完成评审。

先核对仓库指令、目标路径及 `git status --short`。明确区分暂存、未暂存、未跟踪内容与分支提交；按请求读取对应 diff，不能只看 `git diff` 就声称覆盖了全部本地改动。没有 Git 时按用户给出的文件或改前/改后副本审查。

用户给定比较基线就使用该基线；审查分支新增变更时核实目标分支及 merge-base，不擅自将 HEAD~1、main 或整个工作树当基线。缺少会改变评审结果的范围信息才询问；能从上下文明确定义的部分直接推进。

记录实际查看的文件和限制。生成代码、第三方和构建产物默认不逐行审查；若缺陷源于生成模板/配置，追到其来源。项目/解决方案范围需要核实成员、Compile 包含关系、链接文件及目标框架，不能用父目录递归扫描冒充工程覆盖。

范围包括 `.xaml` 及关联 code-behind、ViewModel、资源字典和实际构建/发布配置，不因扩展名不是 `.cs` 就跳过。C# 改名或契约变更也需反查 XAML 消费者；只看 XAML 时按需追到其 C# 来源，不能把绑定表达式当普通字符串或仅检查 XML 能否解析。

## 2. 从变更追到行为

1. 先读需求、提交说明或调用契约，再看 diff 和完整方法/类型；覆盖被删除的逻辑，不只看新增行
2. 沿受影响的输入、返回值、状态写入、外部副作用和失败路径追踪；按需要检查接口实现、partial、调用者、DI 注册、XAML/配置、序列化及源码生成器
3. 阅读 [行为、生命周期与设计审查要点](references/correctness-checklist.md)，只展开代码实际涉及的领域。沿实际创建、重复使用、失败退出和停止路径核对生命周期，沿现有业务流程核对职责与状态边界；核实 .NET/C# 版本、平台、同步上下文和配置，不把某个版本或框架的行为当作通用事实
4. 涉及 XAML 或其消费者契约时，读取 [XAML 联动审查](references/xaml-review.md)，按实际框架追踪绑定来源、资源、事件和更新路径
5. 综合评审及交付主题读取 [主干交付检查](references/delivery-check.md)，核对个人本机调试残留及其构建、配置和运行入口；用户只看其他单一主题时不扩展范围
6. 综合评审随后检查格式；先读 [格式评审边界](references/compliance-check.md)，审查 C# 格式再完整阅读 [代码规范](references/代码规范.md)。XAML 采用项目的 XML/XAML 约定，不套用 C# 声明注释和成员布局规则；纯功能主题无需加载格式规范
7. 对每个候选构造具体输入、调用顺序或线程交错，反查上游约束、现有保护和测试；有反证就撤销或收窄结论，不为凑数保留

变更评审中，原来就存在且没有被本次修改影响的问题不算新增缺陷；只有新路径、调用频率、生命周期或契约变化使其成为本次风险时，说明这条因果链。历史严重问题若值得提醒，单列为既有问题，不混入本次回归数。

改名、删除或重排要核对外部契约，尤其是 public API、持久化名称、绑定、反射、`nameof` 输出和初始化顺序。零文本引用不能证明无用，编译通过不能证明外部消费者兼容。仅有潜在外部依赖而无证据时写成待确认项，不断言已经破坏。

## 3. 形成有证据的问题

功能与生命周期问题应能回答：**在什么条件下，哪段代码会导致什么可观察后果，为什么现有保护没有阻止它**。静态推导明确的越界、资源失效、引用保留或竞态可以报告，不强制先运行复现；关键前提未确认时，说明缺口而不是伪造确定性。

- 位置指向最小相关代码范围；变更评审优先定位当前版本的变更行，并补充必要调用点。不要把整个类或无关格式行当定位
- 一个根因合并一条，列代表性位置与影响范围；不同根因分别报告。修复建议保持最小、可执行，不顺带要求整体架构重写
- 设计/可维护性问题用“位置与依赖关系 → 当前修改或验证必须承担的代价 → 最小改善边界”说明，不仅贴“面条代码”“违反 SOLID”标签。可以报告尚未造成运行故障的实质结构风险，但不能只凭未来可能扩展、函数行数、参数数量或缺少某种模式判错
- 缺测试不自动证明实现错误。能指出关键行为变化及具体未覆盖场景时才给定向测试建议；纯覆盖率偏好不作为功能缺陷
- 安全问题指出实际输入边界、数据流、权限检查和敏感操作；性能问题指出调用链及规模。没有测量不声称百分比提速，没有可达路径不虚构攻击或高频瓶颈

### 结论复核

每条拟确认问题交付前再次核对：位置是否属于受审版本，是否读完相关方法/标记及来源，触发条件是否满足真实契约，现有保护、框架机制或调用方是否已经消除问题。涉及配置或跨文件行为时同时提供消费点与来源证据，不以搜索零命中、类型名、注释或脚本候选替代确认。

把事实与推断分开：静态因果链完整时可以确认，不必虚构运行复现；关键前提如 DataContext、资源加载路径、条件符号或外部契约无法核实时，列为待确认项并说明缺哪项证据，不用确定性标题/严重度冒充已证实缺陷。已被反证的候选直接撤销，不靠“可能”二字保留错误结论。设计风险仍按当前维护代价判断，不能因尚未出故障就忽略大段同职责复制。

复核改进方向是否真的解决根因、保留现有契约且不引入明显新问题。不能承诺“绝对无误报/无遗漏”或用自评分代替证据；未确认问题表示在已覆盖范围内没有足够证据，不表示代码已经获得全面安全或合并批准。

优先级按后果和触发范围，而不是按涉及的关键字决定：

| 等级 | 使用条件 |
|---|---|
| P0 | 无需特殊前提即可造成广泛不可用、严重数据损坏或同等级风险，应立即阻止交付；极少使用 |
| P1 | 在已证实的常见路径或明确支持的条件下有重大功能、数据、安全或兼容性后果，应优先修复 |
| P2 | 有具体可触发条件及实质影响的局部缺陷，或已有明确代价的设计障碍，正常安排处理 |
| P3 | 有明确依据但影响较低的改进；单纯样式问题优先放独立格式小节 |

用户提供项目分级标准时按其标准执行。普通缩进、region 或注释句号不包装成高优先级 bug；若明确导致构建门禁失败或误导调用契约，按实际后果解释。

## 4. 验证与只读边界

优先利用现有测试、编译诊断和小范围的逻辑推演。准备运行命令前检查项目脚本、MSBuild 导入和测试夹具的副作用；build/test 也可能写文件、连接外部服务或执行自定义任务，不因名为“验证”就默认无害。

- 仅执行任务允许且副作用可控的本地验证，产物写入获准目录。用户要求不执行命令/不写文件时遵守，静态审查照常完成
- 不为片段评审创建工程，不为跑工具擅自安装 SDK/包、改 `global.json`、升级依赖或修改测试期望。测试需要新权限、网络或外部环境时报告限制
- 若使用 `dotnet format` 取证，先确认 workspace 与文件范围，只用适用的 verify 检查，不执行会修复源码的模式；单 `.cs` 文件不是 workspace
- 记录实际命令、选择的配置/测试和结果；非零退出可能是工具故障或基线问题，不能一概归因于本次变更。零用例、全跳过、缺报告和未运行不算测试通过
- 依赖不可用不阻止报告静态证据充分的问题，但要区分“静态确认”“已执行验证”“仍需确认”。测试通过、格式零命中均不能保证无缺陷

## 5. 交付评审

优先遵循用户的输出格式。默认先列实际问题，按优先级排序；没有可确认的功能问题就直说，不强行凑发现，也不宣称代码绝对安全。

每条确认问题包含 `优先级 + 简短标题`、`文件:行号`、触发条件与后果或当前维护代价、证据以及最小改进方向。区分功能/生命周期缺陷、设计/可维护性风险、主干交付违规和格式问题；没有运行故障不等于没有设计或交付问题，同一根因也不要跨分类重复报告。必要时给一条定向测试建议，不粘贴整段重写实现。格式问题按同一规则合并并给实际位置；待确认问题单列，明确缺什么信息，不混入确认问题计数。

末尾简述实际覆盖范围、已执行/未执行的验证和限制。未发现功能问题但存在格式问题时，两者分别说明；不能用“总体很好”掩盖尚未验证的关键路径。不自动给合并批准、性能承诺或虚构质量分数。
