# Code Refactor

以当前代码的实际问题为依据，在用户指定范围内改进结构。判断依据是职责、依赖、可读性和验证证据，不是满足行数或抽象数量指标。

## 1. 按请求确定工作方式

| 用户意图 | 执行方式 |
|---|---|
| “只看不改”“扫一下异味”“评估可重构点” | 只读检查，给出有依据的建议；不修改源码、配置或测试 |
| “把 X 改名为 Y”“提取校验函数”“优化这段查询”，或明确要求重构一个局部范围 | 检查影响后直接完成已授权的修改；必要时简述实施顺序，不重复请求确认 |
| “重构整个项目”“看看有哪些地方值得大改”等范围开放、方案有重大取舍的请求 | 先在指定范围内列候选清单和风险，推荐优先项，等用户选择后实施 |
| 已选清单项，或“这些全部做”“你判断并完成” | 在已有授权范围内自主推进；只有新增的外部契约变更、范围扩张或关键选择才需要澄清 |

纯 bug 修复、新功能、迁移和纯格式化按其实际任务处理，不必先让用户重新确认任务名称。混合请求中，将行为变更和纯重构划为可独立审查的改动单元，按依赖选择顺序；已经明确授权的部分直接做。重构中偶然发现的 bug 先报告，不顺手改掉原行为。

C# 纯风格、成员布局和注释合规可使用环境中可用的 `format-csharp`；其他语言优先沿用项目已有格式工具。只读异味检查由本 skill 自包含完成，不依赖额外 review skill。

## 2. 建立影响范围与行为基线

先读目标实现、相关调用点和项目约定。用 `rg` / `rg --files` 定位；有语言服务时结合符号引用，尤其避免把同名符号当成同一依赖。用户只给代码片段且没有项目时，基于片段完成可确定的工作，说明无法检查仓库级依赖。

### 工作区与隐式依赖

- 有 Git 时检查 `git status --short` 和目标文件的 staged / unstaged 差异。保留用户已有修改、未跟踪文件和暂存状态，脏工作区本身不阻止重构。无 Git 时用目标文件的原始内容或临时快照建立基线
- 记录自己要改的具体内容；复杂修改可在独立临时目录保存原文。修改前重读有并发改动的目标，撤回时只撤本次自己的改动，不按文件执行会覆盖用户工作的整文件还原，不自动 stash / commit
- 基线副本、探针、报告和构建产物放在本次允许写入的位置，系统 Temp 不自动扩大授权。优先使用工具支持的标准输出或无缓存检查，不为验证修改全局配置、技能包或无关测试
- 按改动类型查隐式依赖：反射、动态加载、DI / 插件注册、框架入口、事件绑定、路由、配置、序列化、数据库映射、公共 API、监控名称和生成器输入。生成或第三方代码通常从源配置处处理，不直接重写产物
- **重命名属性不等于可以改存储协议**：例如 `dataclasses.asdict(obj)` 或基于约定的 JSON 序列化可能使用属性名作为键；需检查实际序列化器和显式别名。ORM 属性改名也可能改变约定列名，应保留原列映射；数据库迁移属于单独的行为 / 数据变更，不是重命名的默认附带操作
- **零文本引用不证明无用**：入口、导出 API、框架约定、反射字符串、插件发现、条件编译和仓库外消费者都可能绕过普通搜索。无足够证据时把删除列为待确认候选

### 先明确要保持的契约

从实现、测试和调用者归纳与本次修改有关的约束，重点检查：

- 返回值、空值、重复元素、相等性 / 比较器、排序与稳定顺序
- 异常类型、抛出时机和传播方式；取消、超时及资源释放时机
- IO、日志、事件、外部调用的次数和先后顺序；事务边界和部分失败结果
- 状态更新、对象身份 / 共享引用、线程安全、幂等性和重入行为
- API / ABI、序列化格式、存储映射，以及确有依赖的公开诊断信息

性能优化允许改善耗时或内存，但不默认授权改变调度、副作用或一致性语义。对公开 API 改名 / 签名变动，若无法同步所有消费者，保留兼容入口；不能把“仓库内编译通过”当成外部兼容性证据。

### 选择基线验证

从项目文档、构建配置、测试脚本或 CI 推断已有验证命令，优先运行覆盖本次影响范围的定向测试和相关构建 / 类型检查。共享基础组件、广泛签名变更等影响较大时，再扩大到相关集成测试或完整套件。

记录改前已存在的失败、跳过和环境限制，改后使用相同条件比较。没有测试不机械阻断：小范围等价变换可用编译、类型检查、局部运行和 diff 语义检查；复杂逻辑优先补少量可复现现有输入输出、异常或副作用的特征测试，再修改实现。不为通过测试而固化已明确要修复的 bug，不改测试期望来掩盖意外行为变化。

验证不足且无法建立等价性的高风险候选先保留原实现，说明缺的证据；继续完成可独立验证的已授权工作。

自建或修改行为测试、使用旧新实现差分探针，或测试通过却缺少实际执行证据时，先读 [行为验证可靠性](references/behavior-verification.md)。先确认目标逻辑确实执行，再核对具体预期；两边抛出相同异常、零用例或全跳过不能支持行为通过声明。

验证项目应有不同的证据用途。已有测试已导入并执行本次 Python 文件时，不再为了重复证明语法正确追加 `py_compile`；仅需语法检查可在内存中 `compile`，不执行模块。`python -B` 可避免普通导入的字节码缓存，但不会阻止 `py_compile` 显式写 `.pyc`，也不控制测试框架自己的报告或缓存。

## 3. 用证据选择改动

开放范围请求使用简洁清单，每项给出位置、具体问题、建议、影响 / 风险和验证方式。只列用户范围内值得做的机会，不把所有可改写处凑成清单。明确的小任务可直接用一段话说明。

| 风险 | 判据与处理 |
|---|---|
| 低 | 局部等价变换，依赖和副作用明确；可把相关小改动合并验证 |
| 中 | 跨模块、改变内部签名或移动职责；同步调用方，以可验证单元推进 |
| 高 | 外部消费者不明、动态契约、并发 / 延迟求值、缓存 / 事务等；先建立更强的契约证据或兼容方案，证据不足不实施该项 |

行数、参数数、重复次数和实现数量都只是线索：50 行函数、500 行文件、4 个参数、Rule of Three 不是强制阈值。两处相同业务规则也可能值得提取；三处表面相似但变化原因不同，不必抽象。单实现接口可能承担 DI、测试替身、模块隔离或稳定 API 的作用，不能仅凭实现数量删除。

异味清单应解释实际代价，例如职责混杂、同一规则修复需要改多处、参数易传错、依赖循环或重复查询。解释“为什么”的注释、合理的领域类型、内聚长函数和明确边界的接口本身不是异味。

## 4. 按可验证单元实施

一次完成一个逻辑完整的变换及其必要调用方修改。多文件编辑可以跨多个工具调用；在单元完整后再构建和测试，不把编辑途中的暂时编译失败当成最终错误。大规模迁移可用“引入兼容入口 → 迁移调用方 → 证据充分时移除旧入口”，不无故扩大改动。

修改后检查 diff、定向测试及相关构建。若出现新失败，暂停后续独立重构，先判断是否由当前改动造成；已授权范围内修复自己的问题并重测，或精确撤回当前单元。需要改变原契约才能通过时报告原因，不悄悄改断言。不要把已存在的失败归因于本次修改。

### 常见操作的检查点

| 操作 | 关键判断 |
|---|---|
| 重命名 | 先确认符号及实际引用，再改声明和调用；不做无上下文全文替换。复查旧名剩余命中并逐条分类，兼容入口、存储键和有效文档不要求清零 |
| 提取函数 / 变量 | 给职责或复杂逻辑命名；保留求值次数、短路、闭包捕获、返回 / 抛出 / await / yield 位置、资源生命周期和副作用顺序。避免把依赖当前状态的表达式提前计算 |
| 消除重复 | 比较各处语义、变化原因和例外；只抽真正共享的规则，依职责和依赖方向选位置，不机械放进 utils 或目录共同祖先 |
| 简化分支 | 验证早返回没有跳过清理、事件或事务收尾；条件合并不改变求值顺序。三元表达式是否展开由可读性决定，不作一刀切 |
| 删除代码 | 联合引用、可达性、导出 / 注册和配置证据；删除整文件还需检查构建清单、导出入口及生成器。版本历史能恢复不等于代码可安全删除 |
| 拆文件 / 提取类 | 按内聚职责和依赖方向拆，检查循环依赖、可见性、静态初始化及实例生命周期；按兼容性需要保留原入口，不为每次局部移动增加空壳 |
| 调整签名 | 检查命名参数、默认值绑定、重载解析、虚方法 / 接口、委托和反射；新增可选参数也不天然低风险 |
| 引入或移除抽象 | 用当前的替换需求、测试边界和依赖隔离证明收益，比较新增间接层成本，不按实现数量决策 |

C# 重构中新增或改写的注释沿用 `format-csharp` 的约定：`<summary>` 开始标签、内容、结束标签各占独立 `///` 行；用简短短语描述职责 / 目的 / 属性含义，实现原因只在必要的代码逻辑处注释；注释结尾省略中英文句号，保留数据、URL、版本号内的点及省略号。默认只检查本次改写的注释，不扩大为全项目格式清理。

## 5. 性能与算法优化

用户明确要求降低复杂度或优化具体热点时，可以建立代表性基线后实施，无需先让用户提供 profile。开放扫描中则优先推荐有调用频率、数据规模或测量证据的瓶颈，不为理论数字添加无必要缓存或并发。

| 变换 | 必须核对的语义 |
|---|---|
| 嵌套查找 → 索引 / 哈希表 | 首个 / 最后一个匹配、重复键、遍历顺序、相等比较器、空值和额外内存；顺序取决于语言和数据结构，不能笼统假设都无序 |
| N+1 查询 → 批量查询 | 事务与读取快照、排序、参数上限、缺失记录、权限过滤和部分失败 |
| 缓存 / memoize | 数据新鲜度、失效策略、生命周期、内存上限、键比较、对象共享、并发访问及副作用次数 |
| eager → lazy / generator | 执行与异常时机、重复枚举、一次性输入、枚举器释放和捕获的可变状态 |
| 并行 / 异步化 | 结果与副作用顺序、取消、异常聚合、线程亲和性、共享状态；这些往往需要单独的行为变更授权 |

验证应同时覆盖语义和性能：

- 用相同代表性输入比较改前改后的返回、异常和可观察副作用；加入与变换有关的空输入、重复、排序、失败等边界
- 优先复用已有 benchmark；没有时可在授权写入位置建立最小可复现测量，不必为常规本地验证重复询问。使用相同构建模式与环境，必要时预热并重复运行，报告输入规模、样本量、统计结果及明显波动；关注时间和内存之间的取舍
- 计时范围需与收益主张一致，例如计入每次都要构建的索引，区分缓存冷启动和命中；异步操作等到实际完成，消费延迟结果，避免用未执行的工作或计时外的开销证明“变快”
- 运行时、依赖或数据不具备时，用复杂度分析 / 操作计数说明可证实的改善，明确未实测。不把 Big-O 改善、一次计时或测试全绿等同于实际性能和全面行为一致

## 6. 交付

简洁说明实际完成的改动和收益、验证命令 / 结果、未执行的验证及限制。验证结论区分命令退出、有效用例及实际检查的契约；自测装置失效时撤回相应通过声明，修正后重跑，未重跑就标为未验证。对跳过的候选说明具体原因；只读检查给出问题证据和建议，不声称已修改。检查最终 diff 只包含任务所需改动，并保留用户原有工作。

完成授权变换和相应风险验证后交付；源码、配置与测试输入未变且没有新发现时，复用已有验证，不再追加同用途探针。工作区不必变成完全干净：用户原有改动和可说明的验证产物不是失败。

临时产物清理不是交付前提。确需清理时仅处理本轮记录且获准删除的确切路径，不按通用缓存名或公共前缀搜集文件。清理被策略拒绝后保留并说明，不通过换工具、拆分命令、逐文件删除或构建清理继续同一操作；正常参数错误与明确策略拒绝要区分。

行为测试、构建和 diff 分析是互补证据；测试通过不是等价性证明，静态检查也不能覆盖时机、顺序和外部消费者。结论与已经获得的证据一致，不虚报“行为完全一致”或“性能大幅提升”。

标为“实测”的示例须对应实际执行的输入、初始状态和输出；为解释而简化或推导的示例明确标为推演，不冒充执行记录。
