# Tech Design Writer

把“做什么”转成可评审、可实施、可验收的技术设计。默认交付能支撑当前决策的方案：明确实现承载、关键契约、失败边界和验收方式。详细排期、容量测算和实现清单由请求或具体风险触发，不是每份设计的必填内容。

## 适用范围

- 编写或增量更新技术方案、架构选型、数据与接口设计、工程任务和实施路线
- 用户只问一个功能如何实现或只要工期分析时，聚焦该问题，不强行生成整份文档
- 纯阅读、评审或解释请求只读并回答，不据此修改设计文件
- 混合“设计 + 实现”请求先完成必要设计，再继续已获授权的实现，不重复询问是否接着做；实现部分不受本文档模板约束
- 不因设计需要而擅自改 PRD、创建云资源、执行迁移或修改生产配置

## 1. 读取需求与已有约束

优先读取用户指定或上下文已确定的 PRD、需求文档及对应技术设计，文件名不要求符合 `PRD-*.md`。用户直接提供的明确需求文本也是有效输入，不要求先另存一份 PRD。

未指定输入时，先用 `rg --files` 查找相关需求与设计文件，再按产品名、当前任务和已有引用定位。只有存在多个同样合理的目标时才问用户选哪份；没有需求来源且当前信息不足以确定做什么时，询问最关键的缺口，不凭空补产品功能。

读取范围至少覆盖本次功能、前置依赖、验收标准、非功能约束和排除项。已有项目还应检查与决策相关的真实材料，例如依赖声明、部署约束、数据模式或接口规范；不要把仓库里“没有找到”写成“系统不存在”。

文首注明输入路径或会话需求来源、覆盖范围及日期。保留已有 F 编号、优先级和含义；无编号需求可用原章节或条款引用，不擅自给原 PRD 重编号。多份 PRD 有相同 F 编号时使用 `文档名#F001` 区分。

## 2. 按缺口澄清，不重新访谈

从当前需求判断哪些运行环境、兼容性、性能或安全信息会改变方案，只追问这些缺口。不为六维分析、选型比较等方法额外生成一套与交付物重复的表单。

处理方式：

- 已有答案直接沿用，不为走流程再问；对当前场景无意义的维度不强行引入组件
- 用户明确指定选型或要求替换时，这就是本次修改依据；先说明必要影响后实施，不再要求确认同一个选择
- 用户说“你推荐/你决定”时，在授权范围内给出有理由的选择并继续。区分“按用户授权采用的建议”和“仍待用户决定”，不要把委托选择重新变成审批
- 仅当缺失信息会改变产品范围、安全边界、关键兼容性或重大成本，且用户未授权取舍时，聚焦少量关键问题暂停相关决策；其他不受影响部分可以继续
- 低影响细节可采用与现有项目一致的选择；会影响结论的假设明确标注，不写成用户已确认的事实
- 未知性能目标、人数或日期写“未提供”及验证方式，不编造默认 DAU、QPS、工期或合规等级

用户允许先出草案时，将未定事项及其影响集中列出，并标明草案状态。等待时长、用户沉默和“这是演示”都不等于授权替用户决定。

## 3. 先校验边界，再设计

以需求约束为边界选择方案，说明关键取舍和适用条件。优先复用能够满足要求的已有能力，不默认单体、微服务、Redis、消息队列、JWT 或任一云厂商。

若建议方案与 PRD 冲突，先尝试在需求边界内调整方案。仍无法兼容时，引用具体条款，说明证据、影响及可选取舍；不要为迁就方案悄悄修改需求或降低验收标准。用户明确提出的需求变更也要检查依赖影响，仅对新增的未授权取舍提问。

数值必须注明性质：需求目标、已有测量、外部来源或估算假设。实测结果需有测试条件与来源；无实测就给验证方法，不虚构“通常实测”。只有目标影响方案可行性时才作必要估算；详细容量或工期分析使用下方的实施规划参考。

## 4. 写作深度与结构

用户指定路径、文档结构或深度时优先沿用。否则新文档命名为 `TECH-DESIGN-产品名.md`，放在需求文档附近；仅有会话输入时放在当前工作目录。更新已有设计时保持有价值的组织与链接，不为套模板重写全文，也不额外创建 `transcript.md` 等日志文件。

新建文档需要组织结构时，读取 [文档结构参考](references/文档结构.md)；局部修改沿用已有结构，不重新套模板。

### 在目标文档中完成设计

必要输入与核心取舍明确后，在授权目标中按“来源需求 → 实现承载/关键契约 → 验收方式”落稿；共享规则集中定义并引用。先让本次全部范围形成最小可评审闭环，再增加不影响正确性的实现细节；不是先填空模板，也不以待办清单代替设计。影响一致性、兼容性和失败恢复的细节本身就是闭环的一部分，不能留成“后续补充”。

增量更新直接修改受影响的完整小节，保留其他内容。确实未决的事项标明影响，其余部分继续完成。首版后按下方脚本定位结构/引用缺口，再人工核对契约与验收；不因检查通过宣称语义完整，也不在输入未变时重复全文推演。

默认围绕以下关系组织内容，能在同一段或表中说清的不用另设章节：

1. 范围与依据：需求来源、本次功能、已确认约束、排除项和重要假设
2. 架构与选型：模块职责、进程/设备/信任边界、依赖方向、数据流和选型理由
3. 数据与状态：关键实体、关系、约束、状态迁移、资源所有权及持久化边界
4. 关键契约：模块 API、HTTP/RPC、事件、文件格式或设备协议中实际适用的部分
5. 验证与落地：需求如何验收、关键风险如何验证、实现时需要遵守的依赖顺序；用户要求任务拆分或排期时再展开完整实施计划
6. 未决项：缺失信息、阻塞的决策、负责人或下一步验证方式（已知时）

### 关键契约按风险展开

当前交付范围内跨团队/模块边界、影响数据一致性或承载核心流程的契约，应明确：

- 输入/输出的关键字段、类型、必填性、值域、单位及语义
- 调用主体、权限或信任前提，成功条件、失败语义及错误反馈
- 有状态操作的前置状态、并发冲突、重复调用/重放行为
- 异步操作的完成通知、超时、取消、恢复及资源释放责任（适用时）

非关键内部接口不必逐一列出；只标记当前实现仍需补齐的契约及其完成条件。已有 OpenAPI、IDL 或协议定义可引用权威版本，不复制出第二份易漂移的契约。没有网络接口的应用不必制造 HTTP API，也不强制 JSON 响应包、分页形式或网关。

默认写清成立条件而非完整实现：约束表、状态转换或简短伪代码足以说明时，不展开全量 SQL、辅助方法和全部 DTO；影响兼容性、一致性或失败恢复的字段与原子边界仍需明确。同一关键规则在一处定义，其他章节引用并说明各自影响，不重复整段铺陈。

### 按风险展开可靠性与安全

涉及身份与敏感数据、外部副作用、重试、并发写入或数据迁移时，先读取 [可靠性与安全参考](references/可靠性与安全.md)，只应用相关部分。安全基线和失败处理属于已有功能的必要设计，不是新增产品功能；不适用的控制不要堆成章节。

### 图与示例

当架构边界、状态变化或依赖关系用图更清楚时使用 Mermaid；简单局部方案不强制出图。关系模型适合 ER 图，生命周期适合状态图，跨组件交互适合时序图。图文保持一致，节点标签简短；不要人为限制节点数或把一段实现说明塞进节点。

代码围栏应正确闭合。说明中嵌套 Markdown 示例时，外层用四个反引号、内层用三个；最终文档的 Mermaid 使用真实 `mermaid` 围栏，不输出转义的反引号。示例只用于解释选定方案，不能将示例中的业务字段、地域规则或组件变成默认需求。

## 5. 按需展开实施规划

用户要求任务拆分、阶段路线、工作量/容量分析，或更新已有任务与排期时，读取 [实施规划参考](references/实施规划.md)。常规方案只需说明影响落地的依赖及验证，不主动为每个接口建立任务、工时和追溯表。

保留来源的功能编号和产品优先级；交付阶段另行表达，不把 P0/P1 改成阶段编号。用户指定的全部范围都要覆盖，不能通过省略低优先级功能或必要测试缩小请求。前置能力不能晚于依赖方可用。

## 6. 追溯与增量更新

保留已有需求、契约、任务编号及其历史最高号，不因排序重编或在删除后复用。需要新增契约/任务编号时按 [实施规划参考](references/实施规划.md) 的编号约定维护；没有编号需求的短方案可用明确的名称与来源条款关联，不为格式制造 A/T 条目。

核对当前范围的 `需求 → 实现承载/关键契约 → 验收`；有任务清单时再关联任务。承载可以是模块、数据或状态，不要求每项需求都有数据库和 API。基础设施/安全措施需说明支持的真实约束，不能创造产品功能。

增量变更先检查相关引用和下游影响，再一致地更新：

- 需求变动：架构边界、数据、契约、任务、验收和路线图
- 技术替换：兼容性、功能差异、迁移/回退条件、运维要求和估算
- 删除或撤销：前置依赖、遗留引用、已分配编号及需要保留的历史决策依据

明确的更改请求不需要再次确认同一件事；发现请求之外的破坏性取舍时暂停那部分并说明。文档中的迁移方案不构成执行迁移的授权。

## 7. 交付前检查

当前范围形成“需求—实现承载/关键契约—验收”闭环后，对实际文档做定向复核。修复具体冲突、遗漏或断链；仅有措辞偏好时不重写已满足请求的章节。文档和相关输入未变时复用已有检查结果。重大未决项阻塞相关决定，不阻塞用户已允许先写的确定部分。

需要定位实际文档中的机械缺口时，使用只读 `scripts/check-design.py`（Python 3.10+，标准库）：

```text
python -B "<skill-root>/scripts/check-design.py" "<设计文件>" --json
python -B "<skill-root>/scripts/check-design.py" "<设计文件>" --requirements "<PRD 文件>" --require-id F001 --require-id F003 --json
```

第二条只检查明确在本次范围的编号；省略 `--require-id` 时使用该 PRD 中受支持标题定义的全部 F 编号，无编号需求只用第一条，不为脚本重编需求。脚本检查顶层围栏、空正文、A/T 标题定义与最高号，并报告 F 编号显式引用缺口、没有正文的小节候选；不识别任意表格定义/嵌套 Markdown，也不判断引用处是否真正满足需求、契约字段或验收。`0` 表示已覆盖检查无错误，`1` 为结构/引用错误，`2` 为输入或需求来源不可解析；警告仍需人工核对，不能把纯图/代码小节候选直接当缺陷。

提供需求文件时，普通 F 编号按当前来源检查；`路径#F编号` 与简单行内链接须匹配相对设计文件的实际需求路径，其他来源或不能匹配的路径不计入。未提供需求文件时只能查编号出现，不能核对来源。引用式/复杂链接、多行行内代码等完整 Markdown 语法不在覆盖范围内；已有 A/T 标题却缺该类最高号会提示人工核对，不要求无编号短方案新增编号。

- 每个当前范围内需求有实现承载和验收依据；用户要求的任务/排期已覆盖，排除项没有被悄悄实现
- 来源编号和优先级一致；实际存在的契约/任务无重复编号、悬空引用或依赖环，前提没有排在依赖方之后
- 架构图、技术栈、数据模式、接口、状态和任务彼此一致；异步成功不被误写成业务已完成
- 关键流程覆盖成功、主要失败及边界情形；验证方法能检验原验收要求，而非仅证明服务能启动
- 数值有来源或明确假设，工期与容量计算可复算，未知项没有包装为已验证事实
- Markdown/围栏/链接结构正确；有可用渲染工具时检查 Mermaid 实际渲染，没有工具则只报告源码检查，不声称已渲染验证
- 仅更新授权文件，未决事项集中列明，文首范围和日期与实际变化一致

交付时给出完整文件路径（若产生文件）、关键变化和必要的待确认/待验证项。区分已完成设计与仍未验证的性能、外部接口或合规判断，不把文档完成等同于实现完成。验证计划不要求当场执行压测、搭建项目或安装渲染器；不要把这些未授权操作或非必要产物清理变成文档交付的前提。
